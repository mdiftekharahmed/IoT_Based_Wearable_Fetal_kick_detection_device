Yes. That changes the architecture slightly, but in a good way. **Bluetooth should be the local control/diagnostic channel**, while Wi-Fi remains the data-upload channel.

I would make the ESP32 behave like a small state-controlled data logger:

```text
                    ┌─────────────────┐
                    │  Bluetooth App  │
                    └────────┬────────┘
                             │ BLE
              START / STOP / STATUS / UPLOAD
                             │
                             ↓
                    ┌─────────────────┐
                    │      ESP32      │
                    │                 │
                    │ System Manager  │
                    └───────┬─────────┘
                            │
          ┌─────────────────┼─────────────────┐
          │                 │                 │
          ↓                 ↓                 ↓
      Sensors          SD Storage         Wi-Fi
          │                 │                 │
          │                 │                 ↓
          │                 │             Server
          │                 │
          └──────→ RAM ←────┘
```

## 1. Measurement should have an explicit state

Don't just let the sensors run permanently.

Have:

```cpp
enum MeasurementState {
    MEASUREMENT_STOPPED,
    MEASUREMENT_RUNNING
};

MeasurementState measurementState = MEASUREMENT_STOPPED;
```

Then the Bluetooth app sends:

```text
START
```

and ESP32 changes to:

```text
MEASUREMENT_RUNNING
```

The sensor scheduler starts acquiring data.

When the app sends:

```text
STOP
```

the ESP32 stops creating new measurements.

That gives you a clean measurement session.

# 6. Your upload requirement is important

You said:

> button to start uploading data

and:

> schedule upload data, should upload as soon as it gets connection, else store on ram and wait for network

I'd implement that as an **upload manager**.

There are three states:

```cpp
enum UploadState {
    UPLOAD_IDLE,
    UPLOAD_PENDING,
    UPLOAD_IN_PROGRESS
};
```

When you press:

```text
UPLOAD DATA
```

the ESP32 does:

```text
UPLOAD_PENDING
```

Then:

```text
Wi-Fi available?
       │
   ┌───┴───┐
  YES      NO
   │        │
   ↓        ↓
UPLOAD    WAIT
```

It doesn't block the sensors.

# 7. If Wi-Fi is already connected

Suppose:

```text
Bluetooth → UPLOAD
```

and Wi-Fi is already connected.

Then:

```text
UPLOAD_PENDING
       ↓
Wi-Fi available
       ↓
UPLOAD_IN_PROGRESS
       ↓
upload batches
       ↓
server ACK
       ↓
UPLOAD_IDLE
```

Easy.

---

# 8. If Wi-Fi isn't available

Suppose:

```text
Bluetooth → UPLOAD
```

but Wi-Fi is off.

Do **not** do:

```cpp
while (WiFi.status() != WL_CONNECTED)
{
    ...
}
```

That would be horrible.

Instead:

```text
UPLOAD_PENDING
       ↓
Wi-Fi unavailable
       ↓
keep measuring
       ↓
keep SD logging
       ↓
periodically check Wi-Fi
       ↓
Wi-Fi becomes available
       ↓
UPLOAD
```

The user doesn't need to press the button again.

---

# 9. "Store on RAM" needs one clarification

I wouldn't use **RAM as the primary waiting area** for upload data.

You have:

```text
ESP32 RAM
```

which is tiny compared with an SD card.

So I'd do:

```text
Sensor
  ↓
RAM buffer
  ↓
SD card
  ↓
WAIT FOR WIFI
  ↓
UPLOAD
```

RAM is only the **temporary buffer**.

If Wi-Fi is unavailable for:

```text
10 minutes
```

you don't want your RAM filling up.

The SD card should hold the backlog.

# 10. Better upload architecture

I'd make the SD card maintain something like:

```text
/data/
    session_001.bin
    session_002.bin
    session_003.bin
```

and:

```text
/state/
    upload_state
```

The ESP32 knows which files have already been uploaded.

For example:

```text
session_001.bin → UPLOADED
session_002.bin → UPLOADED
session_003.bin → PENDING
```

When Wi-Fi becomes available:

```text
session_003.bin
      ↓
upload
      ↓
server ACK
      ↓
mark uploaded
```

# 11. This gives you offline operation

Imagine you're measuring somewhere with no Wi-Fi.

You press:

```text
START
```

Measurement starts.

Data goes:

```text
Sensors
 ↓
RAM
 ↓
SD
```

Wi-Fi doesn't matter.

Then you finish:

```text
STOP
```

Now you press:

```text
UPLOAD DATA
```

The ESP32 says internally:

```text
UPLOAD_PENDING
```

but Wi-Fi isn't available.

So:

```text
WAIT
```

Later Wi-Fi appears.

The ESP32 detects it:

```text
Wi-Fi connected
      ↓
upload pending
      ↓
upload SD files
```

No data loss.

```text

```

### Wi-Fi


# 17. Overall state machine

The whole device can be represented as:

```text
                    POWER ON
                       │
                       ↓
                  INITIALIZING
                       │
                       ↓
                     READY
                    /     \
                   /       \
             START          UPLOAD
               │               │
               ↓               ↓
          MEASURING       UPLOAD PENDING
               │               │
               │          Wi-Fi available?
               │             /      \
               │           NO        YES
               │           │          │
               │          │          ↓
               │          │       UPLOADING
               │          │          │
               │          └──────────┤
               │                     │
               ↓                     ↓
              STOP                 COMPLETE
               │
               ↓
              READY
```

And importantly:

```text
MEASURING
   +
UPLOADING
```

can happen simultaneously.

## Final system behavior

The finished device should behave like this:

```text
POWER ON
   ↓
Self-test sensors
   ↓
BLE available
   ↓
App connects
   ↓
App sees:
   MPU6050  OK
   BMP180   OK
   MAX30100 OK
   Vibration OK
   SD       OK
   Wi-Fi    Connected/Disconnected
   ↓
START MEASUREMENT
   ↓
Sensor acquisition begins
   ↓
Data → RAM → SD
   ↓
STOP MEASUREMENT
   ↓
Data remains on SD
   ↓
UPLOAD DATA
   ↓
If Wi-Fi available → upload immediately
If Wi-Fi unavailable → mark upload pending
   ↓
Wi-Fi appears
   ↓
Upload automatically
   ↓
Server ACK
   ↓
Mark data uploaded
```

That gives you a proper **field-deployable data logger**, rather than an ESP32 sketch that happens to read some sensors.

And I'd make the next firmware version around **BLE + RTC + binary SD logging + upload queue + your existing sensors**, because those five pieces now form the actual core architecture.
